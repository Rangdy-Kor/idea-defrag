# ⛏️ Minecraft: ONE

---

> [!IMPORTANT] 하나의 플랫폼, 하나의 게임, 하나의 생태계<br>One Platform, One Game, One Ecosystem

Minecraft: ONE은 현재 두 개의 에디션으로 양분된 Minecraft의 생태계를 통합하는 목표를 지닌 가상의 신규 Minecraft 에디션이다.

기존 Java로 작성된 Java Edition은 역사적으로 강력한 생태계를 구축했으나, 장기적인 관점에서는 공식적으로 유지 보수와 통합을 고려하기 어려운 방향으로 진화하였다. 이에 대한 차선택으로 개발된 Bedrock Edition은 대부분이 C++로 개발됐다는 한계 상 충분한 유저 생태계를 구축하지 못하였다. Minecraft: ONE은 바로 이 문제를 해결하고, 공식 지원이 가능한 구조를 만들기 위해 설계되었다.

ONE이라는 이름에는 두 가지의 각기 다른 뜻이 담겨있다. 첫 번째 뜻은 Minecraft의 공식적인 차원들인 Overworld, Nether, End를 나열한 역두문자어이다. 두 번째 뜻은 Microsoft가 자사 브랜드 명명에 주로 사용하는 단어 중 하나인 One의 연장선상이며, 이는 _하&#xB098;_&#xB85C; 통합한다는 Minecraft: ONE의 목표에 대응한다.

## 시스템

---

### 개발

---

Minecraft: ONE은 Unity로 대표되는 상용 엔진 대신 자체적으로 개발된 게임 엔진인 Bedrock Engine을 사용한다. 상용 엔진은 주로 폴리곤 기반의 메시를 사용하기에 복셀 기반 게임인 Minecraft에는 적합하지 않기 때문이다. Bedrock Engine은 C++로 개발된 복셀 기반 게임 엔진이며, Bedrock Edition의 개발에 사용된 실사용 선례가 존재하는 엔진이다.

게임의 근본적인 실행 속도를 결정하는 그래픽 렌더링과 물리 엔진에는 Bedrock Edition과 동일하게 C++을 사용한다. C++은 달리 런타임이 없기에 가비지 컬렉터가 포함되어 있지 않아 게임 도중 발생하는 엔진 레벨의 프리징을 해결할 수 있으며, 이에 더해 개발자가 메모리를 직접 조작하는 경로를 지원하여 타 언어로는 어려운 수준의 네이티브 최적화를 가능케 한다. 단, 이러한 장점에 따른 댕글링 포인터, 이중 해제, 메모리 누수 등의 비정상 종료나 데이터 손상을 유발하는 메모리 해제 관련 오류들을 방지하기 위해 추후 서술할 함수 포인터의 사용을 제외하고는 반드시 스마트 포인터를 사용한다. 추가적으로 메모리 풀링과 단편화 방지를 위하여 최적화가 필요한 부분에 커스텀 얼로케이터를 도입한다.

반면 대부분의 전체 코드 베이스가 C++로 작성된 Bedrock Edition과 달리, Minecraft: ONE은 인게임 콘텐츠 등의 게임 엔진을 제외한 상위 차원 로직에는 .NET 10 런타임 기반의 C#을 적용한다. 앞서 언급하였듯이 C++에 비하면 최적화 측면에서 부족한 측면이 분명히 존재하나, 이러한 선택지를 채택한 이유에는 크게 세 가지 이유가 존재한다.

첫 번째 이유는 고수준 언어의 필요성이다. 앞서 언급하였듯이 게임의 엔진 레벨인 그래픽 렌더링과 물리 엔진 측면에서는 런타임과 GC (가비지 컬렉터)이 없는 C++이 더 적합한 선택지라 판단하였다. 엔진 레벨에서의 일시적인 프리징이나 최적화의 문제는 추후에 예측 불가능한 치명적인 결과로 도래할 수 있기 때문이다. 이는 다르게 표현하자면, 상대적으로 해당 문제들의 영향에서 벗어나있는 상위 차원 로직에서는 LINQ, 패턴 매칭 등 다수의 개발 편의 문법들이 포함된 C#이 부각된다는 뜻이다.

두 번째 이유는 C++과의 상호 운용성이다. C#은 역사적으로 초기부터 C++과의 상호 운용을 고려하고 개발되었으며, 이 때문에 상대적으로 고수준 언어 중에서 C++과의 상호 운용이 가장 수월한 언어라 말할 수 있다. 이러한 장점은 .NET의 최신 버전으로 향할 수록 부각되며, .NET 10 기준으로 `[LibraryImport]`와 함수 포인터를 통해 오버헤드 및 레이턴시를 최소화할 수 있다. 실제로 `[LibraryImport]`와 함수 포인터는 Minecraft: ONE의 개발 시 적극적으로 활용한다.

세 번째 이유는 과거를 상회하는 C#의 완성도이다. 2011년 Bedrock Edition의 전신인 Pocket Edition의 개발 당시의 C#은 .NET Framework라는 Windows에 종속된 전용 런타임에서만 구동되었으며, 실행 속도마저 현재에 비해 현저히 느린 언어였다. 이러한 점으로 인하여 크로스 플랫폼 적합성을 요구하고, PC에 비해 사양이 낮은 모바일 기기 구동을 지원해야 하는 Pocket Edition에는 적합하지 않았고, 결국 Bedrock Edition으로 이어지는 현재까지 C++을 사용하게 되었다.
그러나 10년이 넘는 세월이 흐른 현재, .NET Framework는 크로스 플랫폼을 지원하는 .NET으로 진화하였으며, C# 또한 자체적으로 JIT 컴파일러의 발전과 Native AOT의 지원, `unsafe`로 대표되는 저수준 메모리 제어 기능 등 수많은 개선을 통하여 상용 게임 엔진의 대명사 Unity의 공식 언어가 될만큼 성숙한 언어가 되었다. 이 시점에서 Minecraft라는 대규모 게임 전체를 C++이라는 저수준 언어로 개발할 경우, 최적화 측면에서는 유리한 면이 있으나 지체되는 개발 시간과 불필요한 비용의 상승을 감수해야 한다. 이러한 세 가지 이유에 의해 Minecraft: ONE은 C#이라는 자사의 언어를 상위 차원 로직의 개발에 선택한 것이다.

크로스 플랫폼을 목표로 둔 자체 엔진 게임이 직면하는 대표적인 문제로 플랫폼 별로 상이한 그래픽 API가 존재한다. Minecraft: ONE은 기존 Render Dragon의 구조를 계승하며 오픈 소스 라이브러리 BGFX를 기반으로 한 추상화 레이어를 사용함으로서 해당 문제를 해결한다. BGFX를 사용한다면 DirectX (Windows, Xbox), Vulkan (Linux, Android), Metal (macOS, iOS / iPadOS), AGC (Play Station), NVN (Nintendo Switch) 환경을 하나로 통합된 코드 베이스로 개발할 수 있으며, 이는 코드 베이스의 유지 보수 편의성의 상승과 플랫폼 별 API와 셰이더에서 비롯되는 격차의 감소로 이어진다.

### 배포

---

Minecraft: ONE의 내부 아키텍처는 배포 단계에서부터 실행 파일과 추가적인 모딩 레이어가 철저히 분리되도록 설계되어 있다. 게임 실행 파일이 위치한 본체는 .NET의 최신 기능 Native AOT를 통하여 기계어로 미리 컴파일된 상태로 배포함으로써 실행 성능과 메모리 효율성을 확보하고, 일반적인 경로를 통한 역컴파일을 방지하여 최소한의 보안을 확보한다. 다만 Native AOT는 단일 배포 파일로는 크로스 플랫폼 대응이 불가능하기에 각 플랫폼 별로 배포 파일을 빌드한다.
반면 모딩 레이어는 모딩 파일의 동적 로드 확장성이 요구되기에, 실시간으로 중간 언어로 변환 후 컴파일하는 전통적인 JIT 방식을 사용한다. 소스 코드를 난독화하지 않음으로써 모딩 생태계의 활성화를 유도하며, Native AOT의 자체적인 제약에 더해 `rd.xml`을 제공하지 않음으로써 안정성의 하락과 예기치 못한 크래시의 주범이 되는 리플렉션 의존 코드가 동작하지 못하도록 한다.

Native AOT와 JIT의 공존을 위해서 임베디드 런타임을 사용한다. `nethost.dll`을 사용해 Native AOT 내부에서 JIT 런타임을 부트스트래핑하며, 게임 실행 시 모드 폴더를 스캔한 후 `host.fxr` 라이브러리를 통해 JIT 런타임을 초기화하여 모드들을 로드한다. 이는 Unity가 C++ 엔진 위에서 Mono/IL2CPP를 구동하는 방식과 유사하나, .NET이라는 절대적인 표준을 따른다는 차별점이 존재한다. 이 두 개의 서로 다른 실행 환경 사이의 데이터 교환 시에는 `Shared Memory`와 `Direct Pointers` 구조를 사용하여 복사를 최소화함으로서 오버헤드와 레이턴시를 줄여 안정성을 유지한다.

배포 파일의 물리적인 용량을 줄이고 모바일 및 콘솔 환경에서의 로딩 속도를 개선하기 위하여 Native AOT 배포 시 사용하지 않는 코드를 네이티브 바이너리에서 제거하는 트리밍 기술을 적용한다. 트리밍의 부작용인 리플렉션 및 동적 코드 생성의 실패는 전통적인 리플렉션 대신 소스 생성기를 적극적으로 사용하여 해결한다.

역컴파일과 리플렉션은 Java Edition 모딩 생태계의 핵심 기술이며, 이에 대한 지원을 중단할 경우 생태계 구축에 큰 제약이 될 수 있다는 점을 인지하고 있다. 때문에 Minecraft: ONE은 역컴파일과 리플렉션의 공백을 상쇄할 공식 SDK과 API, 모드 로더, 소스 생성기를 지원하며, 이는 아래의 유저 모딩 부문에 자세히 서술되어 있다.

### 유저 모딩

---

Minecraft: Java Edition의 모딩은 근본적으로 난독화된 게임 실행 파일의 소스 코드를 공식, 혹은 커뮤니티 매핑을 통해 난독화를 해제한 후 역컴파일하여 유저들이 자체적으로 제작한 모드 로더를 통해 모드 파일을 게임 로딩 직전 런타임 단계에서 강제로 주입하는 복잡한 경로의 리플렉션을 사용하였다. 이는 모딩의 높은 자유도와 거대한 생태계를 활성화하는데 직접적인 영향을 끼쳤으나, 모드 간의 빈번한 충돌과 안정성의 하락, 그리고 로딩 시간의 증가와 상당한 메모리 점유라는 크나큰 단점을 앓고 있었다. 이를 해결하기 위해 Minecraft: ONE은 Native AOT를 통해 실행 파일 본체의 역컴파일을 차단하고, 리플렉션의 지원을 사실상 종료하였다. 대신 이들의 대안으로 Minecraft Neo SDK와 MOM (Microsoft Open Modding) API, 내장된 모드 로더와 소스 생성기를 통해 역컴파일과 리플렉션의 공백을 대체한다.

Minecraft Neo SDK에는 개발 편의성과 보안, 안정성을 위한 다양한 기능이 포함되어있다. 그 예시로 모드마다 독립적인 `AssemblyLoadContext`를 부여하는 어셈블리 격리, 개별 모드의 행위 기반 권한 제어, NuGet 지원, Visual Studio 공식 템플릿, 개인의 재시작 없이 C# 코드 수정을 반영할 수 있는 .NET Hot Reloading이 존재한다.

MOM API에는 Event Bus 시스템과 IMC (Inter-Mod Communication) 통신 규격, 추상화 레이어에 대한 지원이 포함되어있다. 모드 로더에는 Java Edition의 Mixin의 공식 대안인 소스 생성기를 통해 런타임이 아닌 컴파일 단계에서 모드를 로딩하여 런타임 성능을 향상시키며, `INotifyPropertyChanged` 등의 로직을 구현할 때 코드 자동 생성, 잘못된 참조의 컴파일 단계 탐지, 로딩 시간의 개선 등 모더의 작업량을 감소시킨다.

C++ 기반의 모딩은 Bedrock Edition과 마찬가지로 안정성의 하락과 보안 위험에 따른 우려에 따라 공식적으로 지원하지 않는다. C# 모드들 또한 각 모드 별 프로세스 격리 기반의 샌드박스 환경에서 실행되며, MOM API로만 통신하기에 C#이라는 강력한 언어가 게임 실행 환경을 탈출해 호스트 환경을 침범하는 일을 방지한다. 단, 프로세스 격리 시 렌더 파이프라인 수정, 엔진 후킹, 바이트코드 패치 등 과거 Java Edition에서의 모딩 문화를 어려워질 수 있으나, Minecraft: ONE은 과거 Java Edition 수준의 무제한 런타임 패치를 공식적으로 지양한다. 대신 앞서 서술한 공식 API와 이벤트 시스템, 소스 생성기 등을 통해 자유도를 보완하며, 사용자가 직접 선택하는 신뢰하는 모드 개념을 통하여 더 높은 권한과 더 깊은 엔진의 접근을 허용할 수 있다.

컴파일 된 C# 모듈의 동적 로드와 별도 런타임 프로세스의 구동을 지원하는 PC 환경에서는 C#을 통한 모딩을 안정적으로 지원하나, 운영체제의 한계 상 이가 허용되지 않는 모바일과 콘솔 기기에서는 이를 대신할 애드온 스크립팅을 지원한다. 이에 대한 자세한 내용은 아래의 애드온 스크립팅 부문에 서술되어있다.

### 애드온 스크립팅

---

Minecraft: ONE의 유저 콘텐츠는 크게 두 가지가 존재한다. Java Edition의 문화를 계승하는 C# 기반의 모딩, 그리고 Bedrock Edition의 문화를 계승하는 TypeScript 기반의 애드온 스크립팅이다. 이러한 두 가지의 개발 경로를 지원하는 선택을 하게 된 계기가 존재한다.

가장 큰 이유는 모바일과 콘솔의 지원이다. C# 모드는 강력한 수정 범위와 성능을 제공하나, Minecraft 사용자의 상당수를 차지하는 모바일과 콘솔 플랫폼은 운영체제 자체의 서비스 정책 상 C#의 동적 로드가 허용되지 않으며, 모딩 레이어의 핵심이 되는 JIT 런타임과 프로세스 격리 구조의 별도 프로세스 구동 또한 운영체제의 아키텍처 모델 상 구현이 불가능하거나 힘들었다.
그렇기에 상대적으로 동적 로드가 자유로운 Android에서는 Chrome에서 사용하는 V8의 불필요한 컴포넌트를 제거한 커스텀 빌드를 게임 내부에 직접 번들링 한 후 TypeScript 애드온은 JavaScript로 컴파일하여 동적 로드를 진행하는 방식으로 구현한다.
서드파티 JS 런타임의 번들링이 앱스토어 정책 상 불가능한 iOS / iPadOS에서는 JIT 컴파일이 비활성화된 Apple의 JavaScriptCore 엔진을 사용한다. 마찬가지로 정책 상 자유로운 유저 콘텐츠의 유통이 허용되지 않는 콘솔 기기 (Xbox, PlayStation, Nintendo Switch)에서는 Marketplace를 통해 Mojang이 직접 검수한 콘텐츠만을 허용하는 방식으로 애드온 시스템을 구현한다.
운영체제의 서비스 정책과 한계 내에서 내린 이러한 선택은, 모바일 기기에서의 C# 모드 사용 불가, iOS / iPadOS와 Android 간의 애드온 성능 차이, 마지막으로 콘솔 기기에서의 제한적인 컨텐츠 등 많은 문제를 동반하나, 이는 플랫폼 정책 상 근본적으로 불가피한 제한에 해당한다.

TypeScript는 모바일 기기에서 동적 로드가 거의 유일하게 허용되는 JavaScript로의 컴파일 완성도가 매우 높으면서도, 타입 안정성이 추가된 상위 호환 언어이기에 애드온 개발에 사용될 언어로 채택되었다. 이에 더해 TypeScript는 MS 자사의 언어이며, Minecraft: ONE을 통해 실무에서 사용하는 언어를 익힐 수 있다는 강력한 마케팅 포인트를 제공한다. 또한 TypeScript는 JavaScript 생태계와 높은 호환성을 유지하면서도 정적 타입 기반의 안정성을 제공하며, 이미 거대한 규모로 구축된 VS Code 및 NPM 생태계를 적극적으로 활용할 수 있다는 장점이 존재한다. 이러한 특성은 웹 개발자들의 유입 장벽을 낮추고, 상대적으로 접근성이 높은 애드온 개발 환경을 구축하는 데에도 긍정적인 영향을 끼쳤다.

정리하자면, 동적 라이브러리의 로드가 허용되는 PC 환경에서는 C#을 통한 대규모 코드 개편을 허용한다. 반면 이가 허용되지 않는 모바일 환경에서는 TypeScript를 통한 애드온 스크립팅을 지원한다. 모바일 및 콘솔 기기에서는 C#으로 개발된 모드를 적용할 수 없으나, 반대로 PC 환경에서는 V8을 통해 애드온을 설치할 수 있다. 또한 C# 모드와 TypeScript 애드온은 동일한 MOM API를 사용하기에 서로를 호출하여 상호 운용할 수 있다. 메타데이터에서 C# 모드의 의존성이 감지된다면 해당 애드온은 모바일에서 설치되지 않는다.

Minecraft: ONE은 모든 플랫폼에서 동일한 수준의 유저 콘텐츠 자유도를 제공하는 것을 목표로 하지 않는다. 대신 각 운영체제와 플랫폼 정책이 허용하는 범위 내에서 최대한의 확장성을 제공하는 것을 목표로 설계되었다. 이에 따라 동적 라이브러리 로드와 별도 런타임 실행이 가능한 PC 환경은 C# 기반의 고급 모딩 플랫폼으로 동작하며, 상대적으로 제약이 존재하는 모바일 및 콘솔 환경에서는 TypeScript 기반의 애드온 스크립팅과 검수 기반 콘텐츠 시스템을 중심으로 생태계를 구축한다. 이는 특정 플랫폼에 대한 의도적인 기능 제한이 아닌, 각 플랫폼의 보안 정책과 실행 구조에서 비롯되는 현실적인 차이에 해당한다.

TypeScript 애드온 개발을 위해 Minecraft Add-on Scripting 확장을 VS Code 마켓플레이스에서 지원한다. 해당 확장은 TypeScript 확장을 사전적으로 요구하며, MOM API에 대한 문법 강조, 자동 완성 등의 개발 지원을 제공하기 위해 배포된다. 또한 Minecraft ONE CLI라는 터미널 시스템을 지원하며, 개발자들은 이를 통해 애드온 프로젝트를 생성하고 빌드하는 등 지원을 받을 수 있다.

애드온의 근본적인 목적은 모바일 및 콘솔 기기에서의 유저 컨텐츠 지원과 간단한 콘텐츠의 추가, 혹은 편의성 등 간단한 시스템의 변경이며, C# 모드와 달리 게임의 근본적인 시스템을 개편하는 것을 전제로 설계되지 않았다.

### 데이터 저장 및 연산

---

Minecraft: Java Edition은 월드 데이터를 저장 시 Anvil 저장 포맷을 채택하여 파편화된 파일들로 청크를 관리하였다. 이는 데이터의 수정이 쉽고 리전 구조가 독립되어 있었으나, 그만큼 청크 파일의 손상과 교체라는 외부 변수에 취약함과 동시에 자바의 I/O 특성과 맞물려 대규모 데이터의 입력 시 입출력의 효율성이 하락한다는 단점이 있었다. 반면 Minecraft: ONE은 Bedrock Edition과 같이 개별 차원별로 존재하는 LevelDB 데이터베이스 파일을 사용하여 파일의 손상과 외부 복제와 교체 등의 게임 외부적인 개입을 방지한다.

렌더 거리 내부의 실체 청크를 로딩하는 데이터베이스 이외에도, LOD 기반의 가상 청크 렌더 거리를 위한 LevelDB 데이터베이스로 시각적 렌더 거리를 크게 확장한다. 실제 렌더링 거리는 기존 32청크에서 64청크까지 증가하나, LOD 가상 청크는 512청크까지 렌더링을 지원한다. 명시적으로 설정된 LOD 품질과는 별개로, 장치의 사양을 자동으로 인식하여 계산된 임계 거리 이상부터는 강제적으로 단계별 품질 저하가 적용된다.

기존의 파편화되었던 NBT, 아이템 구성 요소, 텍스트 구성 요소, 월드 데이터가 모두 구성 요소로 통합된다. 기존 Java Edition의 > NBT 기반 구조는 세부 데이터 접근 시 전체 객체의 역직렬화를 요구하는 경우가 많았다. 대신 Minecraft: ONE은 LevelDB 기반의 키-값 저장 구조를 사용하여 필요한 데이터만 선택적으로 접근할 수 있도록 설계하였다. 모든 상태 데이터는 컴포넌트 기반의 바이너리 직렬화 포맷으로 저장된다. 단, 블록은 개별 객체로 취급하지 않으며, `friflo ECS` 라이브러리를 활용해 데이터 중심 엔티티 컴포넌트 시스템을 도입하고, 해당 라이브러리의 SIMD를 적극 활용하여 대량의 블록 데이터를 효율적으로 처리한다.

LevelDB와 SQLite 모두 갑작스러운 게임 종료 시 데이터 유실을 방지하기 위하여 WAL 모드를 활용해 데이터 무결성을 확보한다.

Scoreboard와 Storage는 모두 각각 지역 변수와 전역 변수라는 개념으로 대체된다. 데이터팩 내부에서 `$`을 사용하는 매크로 기능은 한층 강화되어 서버 관리 콘솔과 인게임 명령어에서도 변수를 명령우 중간에 대입 및 참조할 수 있다. 변수 또한 컴포넌트 형식으로 관리되며, 컴포넌트가 존재하는 모든 객체에 지역 변수를 할당할 수 있다. 전역 변수는 월드 전체에 적용되기에 특정 객체에 할당할 수 없다. 변수 타입으로는 Byte, Short, Int, Long, Float, Double, Char, String, List, Dictionary, Tuple, Object를 지원한다.

Minecraft: Bedrock Edition은 틱 연산에 완전한 비동기 처리를 지원하여 실행 속도를 효과적으로 향상시켰으나, 이에 의해 레드스톤 회로의 오작동 등 수많은 버그들이 발생하였다. Minecraft: ONE은 청크 단위 병렬 파이프라인을 도입하여 플레이어 주변의 핵심 영역은 여러 코어에 분산된 로직을 틱의 마지막에 합쳐 다음 틱으로 넘어가는 포크-조인 모델을 통해 메인 스레드와 동기화된 병렬 연산을 수행하여 논리적 일관성을 유지한다. 시뮬레이션 거리 내의 백그라운드 로직은 .NET의 `Task` 기반 비동기 스케줄러를 통해 메인 틱의 부하를 주지 않는 범위 내에서 독립적으로 연산된다. 단, 모든 멀티스레드 연상 중에서 쓰기 작업만큼은 반드시 메인 스레드의 통제 하에 위치시키며, 비동기 영역에서 발생한 변경 사항을 쓰기 대기 큐에 담아 메인 틱의 특정 시점에 일괄 반영 시킴으로서 데이터 경합과 레이스 컨디션을 원천 차단한다.

### 멀티플레이

---

Minecraft: Bedrock Edition는 Xbox 친구 추가 연동 기능을 통해 복잡한 포트포워딩이나 외부 서비스 없이 멀티플레이를 즐길 수 있도록 하였다. 이는 기술적 한계에 마주친 일반 사용자들도 또한 멀티플레이를 즐길 수 있다는 의의가 있었으나, 자신의 세계 타 플레이어를 접속시키는 로컬 호스트 방식이기에 호스트가 게임을 종료할 시 서버가 유지되지 못한다는 단점이 존재하였다. 때문에 Minecraft: ONE은 호스트의 컴퓨팅 자원을 이용하는 방식을 유지하되, 로컬에서 독립적으로 구동되는 서버 인스턴스를 활용하여 호스트의 접속 여부에 관계 없이 서버가 장시간 유지되도록 한다.

서버를 개설하는 방법은 크게 두 가지가 존재한다. 첫 번째는 완전히 새로운 세계를 만드는 방식이며, 멀티플레이 메뉴에서 새 로컬 서버 메뉴를 통해 개설할 수 있다. 두 번째는 기존 세계를 개방하는 방식이며, 서버로의 전환 과정이 없는 로컬 호스트 방식과, 전환 과정을 거친 후 개설 가능한 로컬 서버 방식이 있다. 로컬 호스트는 선술하였듯이 호스트의 접속 없이는 서버가 유지되지 못하며, 별도의 서버 관리가 불가능하다는 단점이 있다.

로컬 서버는 독립된 서버 프로세스로 실행되며, 게임 클라이언트를 종료하여도 백그라운드에서 유지된다. 단, 호스트 장치의 전원이 종료되거나 운영체제가 서버 프로세스를 강제 종료할 경우 서버 또한 종료된다.

기존 Java Edition의 서버 관리는 서버 구동 인스턴스의 CLI 창으로만 가능하여 진입 장벽이 상대적으로 높았다. Minecraft: ONE은 GUI 창을 도입하여 복잡한 명령어 없이 마우스만으로 2D 월드 대시보드, 서버 규칙 변경, 서버 공지 등의 기능을 사용할 수 있다. 단, GUI는 대부분의 일반적인 서버 관리 작업을 수행할 수 있도록 설계되었으나, 복잡한 자동화 및 고급 관리 작업까지 모두 대체할 수는 없다 판단하였다. 이에 따라 Minecraft: ONE은 GUI와 함께 CLI 콘솔을 제공하며, 사용자는 필요에 따라 두 방식을 병행할 수 있다.

여기서 2D 월드 대시보드는, 월드 전역의 플레이어 위치와 이동 경로, 청크 상태 등을 실시간으로 확인할 수 있는 운영 대시보드 역할을 수행한다. 이를 통해 관리자는 특정 플레이어의 이동 상황을 추적하거나, 이상 행위 및 서버 부하가 집중되는 지역을 신속하게 파악할 수 있다.

서버 관리 체계는 기존 OP / DEOP 이분화 체계에서, 명령어 권한 체계와 통합된 Lv.0~Lv.4의 5단계 체계로 세분화된다.

- **Lv. 0 - Guest**: 한국어 명칭 참여자. 기본 명령어만을 사용할 수 있으며, 싱글 플레이 월드에서 치트를 비활성화하였을 때와 본질적으로 동일하다.
- **Lv. 1 - User**: 한국어 명칭 사용자. 일반 명령어만을 사용할 수 있으며, 신규 플레이어에게 기본적으로 자동 부여되는 권한이다.
- **LV. 2 - Operator**: 한국여 명칭 운영자로, 게임 내부의 운영을 담당한다. 대부분의 명령어를 사용할 수 있으며, 신규 플레이어에게 자동 부여하도록 설정할 수 있는 최대 권한이다. 별도의 설정을 거치지 않을 시 커맨드 블록과 데이터팩 함수의 기본 권한으로 적용된다.
- **Lv. 3 - Admin**: 한국어 명칭 관리자로, 서버 자체의 관리를 담당한다. 모든 클라이언트와 대부분의 서버 관리 명령어를 사용할 수 있으며, 호스트 플레이어에게 자동 부여되는 권한이다. 다른 플레이어에게 부여하기 위해서는 Lv. 4 권한의 서버 콘솔을 사용해야 한다. 커맨드 블록과 데이터팩 함수에게 설정 가능한 최대 권한이다.
- **Lv. 4 - Owner**: 한국어 명칭 소유자. 인게임 플레이어가 가질 수 없는 권한이며, 서버 종료, 서버 저장 / 백업 등을 포함하여 모든 명령어를 사용할 수 있다. 이 권한은 오직 서버 콘솔만이 소유할 수 있으며, 인게임 개체에게 이전하거나 부여할 수 없다.

크로스 플랫폼 간의 멀티플레이는 기본적으로 지원되나, PC 전용 C# 모드에 대한 의존성이나 플랫폼 정책 등에 의해 일부 기능이 제한될 수 있다. 또한 서버 메타데이터 상 클라이언트 측에 요구하는 특정 모드 / 애드온이 있다면, 이를 설치하지 않을 시 접속할 수 없다.

멀티플레이 동기화를 위한 네트워크 프로토콜은 QUIC를 사용하며, 패킷 손실과 IP 변경 대응, 보안성을 확보한다. 기존 Bedrock Edition이 사용했던 RakNet 만의 장점을 흡수하기 위해스트림 별로 `Reliable Ordered` (채팅, 아이템 이동), `Reliable Unordered` (청크 데이터), `Unreliable` (엔티티 움직임) 옵션을 동적으로 할당하며, Zstd 압축 알고리즘을 QUIC에 직접 통합해 기존 zlib 대비 CPU 점유율을 낮추고 압축률은 높인다. 특히 지형 데이터의 전송 시 딕셔너리 압축을 통해 대역폭을 처리량을 절감한다. 이외에도 증분 동기화 로직을 활용해 청크의 변경 사항만 압축하여 전송하는 방식을 사용한다.

### 인게임

---

Minecraft: Java Edition과 Bedrock Edition은 완전히 다른 코드 베이스로 제작되어 기술적으로 별개의 게임에 가깝기에 인게임 콘텐츠 측면에서 많은 차이를 보여 많은 신규 유저들의 혼동을 불러일으켰다. Minecraft: ONE은 이 둘을 하나로 통합하는 목표로 설계된만큼, 원작의 배경과 환경을 고려한 선택으로 로직과 콘텐츠를 통일하였다.

**Bedrock Edition 채택**:

- 가마솥에 물과 용암, 가루눈만을 담을 수 있던 Java Edition과 달리, 물약을 담을 수 있게 된다. 단, 어떠한 유형의 물약이든 가마솥에 상호작용하여 물약을 담을 수 있던 Bedrock Edition과 달리, 투척용과 잔류형을 제외한 일반 물약을 통해서만 가마솥에 물약을 채울 수 있다.
- 상태 효과 화살을 제작하려면 잔류형 물약을 사용해야했던 Java Edition과 달리, 가마솥에 채운 물약에 화살을 우클릭하여 화살에 상태 효과를 적용 시킬 수 있다. 단, 이렇게 제작할 시 상태 효과의 지속 시간이 3분의 1로 감소하며, 가마솥의 용량 1칸을 소모한다. 중복적으로 상호작용하여 지속 시간을 증가시키는 것은 허용되지 않는다.
- 마녀의 집에 위치한 가마솥에 아무것도 담겨있지 않은 Java Edition과 달리, 확률적으로 액체가 담겨있게 된다. 담겨있는 액체의 용량은 25% 확률로 0레벨, 즉 아무것도 담겨있지 않은 상태이며, 나머지 75%는 1-3레벨 중 각각 25%p 확률로 결정된다. 담겨있는 액체의 종류는 28% 확률로 일반적인 물이며, 나머지 72%는 마녀가 전투 / 지원 시 투척하는 종류인 나약함 / 독 / 구속 / 고통 / 치유 / 화염 저항 / 수중 호흡 / 신속 / 재생 중 각각 8%p 확률로 결정된다.
- 가마솥에 담긴 물을 염색할 수 없는 Java Edition과 달리, 염료를 들고 상호작용하여 가마솥에 염료를 용해시킬 수 있게 된다. 염료를 용해시키지 않은 물의 색상은 Bedrock Edition과 같이 생물 군계에 따라 결정된다. 염료를 용해하는 순서나 조합 또한 최종적인 물의 색상에 영향을 주게 된다.
- 아이템 액자와 상호작용하더라도 팔을 흔들지 않는 Java Edition과 달리, 아이템 액자 내부의 아이템을 회전시킬 때 플레이어가 팔을 휘두르게 된다.
- 갑옷 거치대에 팔이 없는 Java Edition과 달리, 갑옷 거치대에 팔이 생겨 손에 아이템을 쥐어줄 수 있게 된다. 웅크린 후에 우클릭하여 왼손에도 아이템을 쥐어줄 수 있다. 단, 이로 인해 자세 바꾸기 키로 갑옷 거치대의 자세를 바꾸는 기능은 제거되며, 특정 단게의 레드스톤 신호를 보내거나 갑옷 거치대 구성 요소를 조작하여 이를 수정할 수 있다.
- 갑옷 거치대의 목과 어깨 부위가 수평을 이루지 않고 랜덤 요소가 존재하는 Java Edition과 달리, 목과 어깨 선이 수평을 완전한 이루게 된다.
- 3인칭 카메라 및 다른 플레이어의 시점에서 음식 섭취, 낚시 등의 모션이 존재하지 않는 Java Edition과 달리 해당 시점에서 1인칭 시점의 모션들이 실제로 볼 수 있게 된다.
- 크리에이티브 및 평화로움 난이도에서 특수 효과를 보유하지 않은 일반적인 음식을 섭취할 수 없는 Java Edition과 달리, 해당 상태에서 어떠한 음식이든 섭취할 수 있게 된다.
- 켈프가 흔들리는 속도가 다소 빠르고 역동적인 Java Edition과 달리, 흔들리는 속도가 상당히 느리고 여유로워지게 된다.
- 블록의 파괴 / 설치 속도가 상대적으로 느린 편인 Java Edition과 달리, 크리에이티브 모드 한정으로 블록의 파괴 / 설치 속도가 Bedrock Edition과 동일한 속도로 향상된다. 비행 중 파괴 / 설치 키를 홀드 상태로 유지하더라도 블록의 파괴 / 설치가 끊기지 않고 지속된다. 단, 서바이벌 모드에서는 Java Edition과 유사하게 파괴 / 설치에 0.3초의 재사용 딜레이가 적용된다.
